# 整合包 · 项目监测

> 示例整合包。格式见 [../../开发文档.md](../../开发文档.md)。
> **本文只写：由哪些插件完成。**

## 1. 目标

持续看住一个已交付的项目，**主动发现问题，产出问题清单**。

**观察型整合包** —— 不改业务代码。发现问题交给代码开发整合包修。

### 1.1 模型策略

```ts
modelPolicy: {
  transport: "api",
  byTaskKind: {
    watch:   ["claude-haiku-4-5"], // 守候是长时轮询，要便宜
    diagnose:["claude-opus-5-5"], // 诊断要能读懂日志和指标
    report:  ["claude-sonnet-5-5"],
  },
}
```

**守候环节的成本是结构性的**：它一天跑几百次，每次的 token 都要乘上去。所以 `watch` 用最便宜的模型，`diagnose` 才换强的 —— **贵模型只用在真需要判断的地方**。

`transport: "api"`：监测是后台轮询，不是一个人在等结果，用不上外部 CLI 的 harness，反而多一个黑盒进程难埋点。

## 3. 套件

| 套件 | 用它做什么 | 离线时 |
|---|---|---|
| `monitor-suite` | 拉取线上指标、日志聚合 | 降级为本地检查 |
| `model-suite` | 异常归因 | 用 `local-model` |

## 4. 状态

```text
讨论 → 计划 → 工作 → 微调修正 → 汇报
```

| 状态 | 在做什么 | 验证 hook |
|---|---|---|
| **讨论** | 确定监测范围、频率、基线 | 监测项已确认 |
| **计划** | 排检查顺序、定阈值 | 检查项可执行 |
| **工作** | 跑检查、对比基线、归因 | 每轮结果已落日志 |
| **微调修正** | 检查项本身配错了 | 重跑确认 |
| **汇报** | **问题清单** | 三段齐全 |

**监测的三个基线信号**：构建、测试、静态诊断。任一由绿转红即产生一条问题记录。

**关键规则**：

| 规则 | 说明 |
|---|---|
| 只报**回归** | 上轮红、本轮也红 → 是存量问题，不重复报 |
| 每条问题带引入提交 | 靠 `git` 二分定位，报"什么时候坏的" |
| 不改业务代码 | 发现了就交接，**不在监测包里顺手修** |
| 阈值是显式的 | 什么算"异常"必须写出来，不靠模型感觉 |

## 5. 交接

### ← 代码开发（入）

带 baseline commit 与已完成目标清单进来，作为对照基线。

### → 代码开发（出，主路径）

```ts
{
  targetPackageId: "code-development",
  trigger: "完成条件",
  requiredFacts: ["projectId", "problemList", "baselineCommit"],
  handoffMapping: {
    "monitor.projectId":     "task.projectId",
    "monitor.problemList":   "task.constraints",       // 问题即约束
    "monitor.baselineCommit":"project.baselineCommit",
    "history.artifactRefs":  "history.artifactRefs",
  },
  prepare: [
    { kind: "promptRules",  value: "code-development/bugfix" },
    { kind: "reportFormat", value: "code-development/change-report" },
  ],
}
```

**问题清单直接映射成 `constraints`** —— 修的时候不需要重新解释"哪里不对"。

### → 语音助手（出）

问题涉及**业务含义**时（"这个功能到底该不该有"）退回需求澄清，不在技术层猜。

## 6. 汇报格式

```ts
{
  id: "project-monitor/monitor-report",
  sections: [
    { key: "completed", title: "完成了什么",     required: true },   // 跑了几轮、覆盖什么
    { key: "issues",    title: "存在什么问题",   required: true },   // 问题清单，含引入提交
    { key: "decisions", title: "需要我做什么决策", required: true },  // 哪些要修、修不修
    { key: "metrics",   title: "指标变化",       required: true },   // 本轮 vs 基线
  ],
  requireEvidence: true,     // 每条问题要带检查输出
  outputFormat: "markdown",
}
```

**问题段是本整合包的主产出** —— 每条含：现象、首次出现的 commit、影响范围、复现命令。

## 7. 权限

| 权限 | 理由 | 必需 |
|---|---|---|
| `fs:read` | 读代码做静态检查 | 是 |
| `process` | 跑构建和测试 | 是 |
| `net` | 拉线上指标 | 否（无 `monitor-suite` 时不需要） |
| `fs:write` | 写监测报告 | 是 |
| `fs:write`（业务代码） | — | **不申请** |

## 8. 降级

| 缺失 | 行为 |
|---|---|
| `monitor-suite` 离线 | 只跑本地三类基线，**明确告知覆盖面变窄** |
| `build-test` 不可用 | 只跑静态诊断，**明确告知无回归检测** |
| `git` 不可用 | 问题无法定位引入提交，**每条标注"来源未知"** |
| `model-suite` 离线 | `local-model` 归因，或只报原始现象不做归因 |
| `sandbox-process` 不可用 | 检查脚本改为主机白名单执行，**明确告知** |

## 9. 验收

- [ ] 构建/测试/静态三类基线都跑
- [ ] 只报回归，存量问题不重复刷
- [ ] 每条问题能定位到引入它的提交
- [ ] **监测包里没有改过业务代码**
- [ ] 交接给代码开发后问题清单直接可用
- [ ] 阈值是配置里的显式值，不是模型判断
- [ ] 汇报恒为三段 + 指标

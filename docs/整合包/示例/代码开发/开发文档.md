# 整合包 · 代码开发

> 示例整合包。格式见 [../../开发文档.md](../../开发文档.md)。
> **本文只写：由哪些插件完成。**

## 1. 目标

把明确的需求，变成**通过构建与测试的代码**。

**主力型整合包** —— 系统里代码产出量最大的模式。TS 单语言，覆盖全部交付物。

### 1.1 模型策略

```ts
modelPolicy: {
  transport: "auto",              // 实现环节允许走外部 CLI
  byTaskKind: {
    plan:     ["claude-opus-5-5"],   // 规划要强推理
    implement:["claude-sonnet-5-5"], // 写代码量大，便宜且快的够用
    review:   ["claude-opus-5-5"],   // 审查要挑得出问题
    test:     ["claude-haiku-4-5"],  // 生成测试是体力活
  },
}
```

**实现环节走外部 CLI 是有意的** —— Claude Code 那套 agent 循环、文件访问、工具链已经调好了，用它等于白拿一整套成熟 harness。规划和审查留在 API 侧，因为那两步要精细控制每一步。

**这里写的是模型名，不是账号 id。** 用哪个账号满足这些模型，是全局 `ModelSelectionPolicy` 的事（见 [../../../开发文档/10-工作台与项目管理.md](../../../开发文档/10-工作台与项目管理.md) §2.3）—— 切便宜的、切强的都不用改这个包。

## 3. 状态

```text
讨论 → 计划 → 工作 → 微调修正 → 汇报
```

| 状态 | 在做什么 | 验证 hook |
|---|---|---|
| **讨论** | 只在需求不清时回退到这里 | 目标表每条任务有验收标准 |
| **计划** | 拆任务、挂目标、定验证方式、建工作区 | 任务可执行性 |
| **工作** | 写 → 格式化 → 构建 → 测试 | `verify.typecheck`、`verify.test` |
| **微调修正** | 构建或测试失败时修 | 修完重跑全部 hook |
| **汇报** | 代码变更汇报 | 三段 + 证据 |

**工作态的硬规则**：

| 规则 | 说明 |
|---|---|
| 先读后写 | 改任何文件前先 `fs.read`，不凭记忆改 |
| 每个任务一个检查点 | 阶段完成即 commit，不等全部做完 |
| 构建不过不算完成 | `ALL_PASS` 的判据是**构建 + 测试**都过 |
| 工具失败不静默重试 | 同样的失败重试第二次是浪费，记入汇报 |

## 4. 交接

### ← 语音助手（入）

由 `transitions` 的 `prepare` 自动准备：

```ts
prepare: [
  { kind: "language",     value: "typescript" },
  { kind: "framework",    value: "react" },
  { kind: "promptRules",  value: "code-development/default" },
  { kind: "reportFormat", value: "code-development/change-report" },
]
```

**不自动决定**：库选型、是否引入新依赖 —— 缺了就问，不猜。

### → 项目监测（出）

代码通过 + 有可观测的检查点后交接。

```ts
{
  targetPackageId: "project-monitor",
  trigger: "完成条件",
  requiredFacts: ["projectId", "commitRef", "checkpoints", "goalTable"],
  handoffMapping: {
    "project.id":             "project.id",
    "project.commitRef":      "project.baselineCommit",
    "task.completedGoals":    "monitor.baseline",
    "history.artifactRefs":   "history.artifactRefs",
  },
}
```

### → 设计转代码（出）

任务里有界面部分时。

### → 语音助手（出）

**需求在实现中变了**（"其实我要的不是这个"）→ 退回需求澄清，不在代码里猜。

## 5. 汇报格式

```ts
{
  id: "code-development/change-report",
  sections: [
    { key: "completed", title: "完成了什么",     required: true },
    { key: "issues",    title: "存在什么问题",   required: true },
    { key: "decisions", title: "需要我做什么决策", required: true },
    { key: "evidence",  title: "证据",           required: true },  // 构建/测试输出、commit
  ],
  requireEvidence: true,
  outputFormat: "markdown",
}
```

**证据段是本整合包特有的** —— "改完了"必须有构建和测试输出支撑。

## 6. 权限

| 权限 | 理由 | 必需 |
|---|---|---|
| `fs:read` `fs:write` | 读写代码 | 是 |
| `process` | 构建、测试 | 是 |
| `net` | 模型调用、依赖安装 | 是 |
| `git` | 检查点 | 否（无 git 降级为文件备份） |

## 7. 降级

| 缺失 | 行为 |
|---|---|
| `lsp` 不可用 | 跨文件跳转降级为 grep，**明确告知** |
| 容器不可用 | 降级为进程级沙箱 → 仍不可用则降级为宿主直跑，**三次都记入埋点** |
| `model-suite` 离线 | `local-model`，能力下降，**明确告知** |
| `git` 不可用 | 检查点降级为文件备份，**明确告知** |
| `build-test` 不可用 | **不允许进汇报态** —— 无法验证的代码不算完成 |

## 8. 验收

- [ ] 从语音助手交接进来后 TS + React + 代码汇报格式自动就位
- [ ] 没读过的文件不直接改
- [ ] 阶段完成即有检查点
- [ ] 构建或测试不过时进微调修正态，**不直接汇报**
- [ ] 汇报带构建/测试证据
- [ ] 改错了能开分支回溯，**历史不被改写**
- [ ] 缺依赖/缺库选型时**主动问**，不猜
- [ ] 汇报恒为三段 + 证据

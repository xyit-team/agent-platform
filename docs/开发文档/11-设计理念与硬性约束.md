# 11 · 设计理念与硬性约束

> 原始素材：`插件逻辑/设计理念.md`（8 条）+ `实现功能.md`（4 条）
> 本文件是全系统的设计律来源。实现时与本文件冲突的方案一律不采纳。

## 1. 八条设计理念

### 1.1 主核心单薄，其他皆为插件

平台底座只做装载、路由、记录三件事。**所有业务能力都在插件和套件里。**

判断某段逻辑该放哪：

| 放哪 | 判据 |
|---|---|
| 底座 | 换任何模式都要用它 |
| 插件 | 只有部分模式用它，且是本地能力 |
| 套件 | 需要云端数据，或需要跨用户共享 |
| 整合包 | 只有某个模式用它，且是编排规则 |

**验证**：拿掉全部插件，底座仍能启动。

**判据问的是「拿掉会不会坏」，不是「有没有人用」。** 这一点有两个例外，不写出来一定会有人按判据把东西挪错地方：

| 例外 | 判据为什么对它失效 | 归属和理由 |
|---|---|---|
| `i18n`（多语言） | **所有模式都用**，判据第一条字面不成立。但拿掉它全库回退源文（＝不翻译），系统照常跑 | **插件**。词条是内容，内容不进运行时；换一整套术语表是组织级配置，不该改核心 |
| 账号（多模型） | 同上，所有模式都用 | **核心**。拿掉它模型调不动，系统真的跑不起来 |

两个不是同一种情况：一个是「拿掉只损失一层翻译」，一个是「拿掉模型就调不动」。**同样的判据失效，结论相反。**

**跨会话派活（[session-hub](../插件/协作/session-hub/开发文档.md)）也是同一个判据的产物**：会话容器在核心里（每条消息都要落到某个会话，埋点也要知道这次执行属于谁），但派活、跨会话读、自然语言拉起新会话都在插件里 —— 拿掉它退回单会话，系统照常。

> **「会话」是编排对象，不是能力。** 判据表按「能力的性质」分三档，会话按「生命周期」分，不在同一个轴上。处理办法和 `agent-pool` 同档：**会话是按它承载的运行时装配能力（跨会话派活、跨会话读）来归类的**，不是按「会话本身」归类。见 [04 §6](04-三大核心对象.md)。

### 1.2 整合包式热加载启动

系统不是"先装一堆东西再启动"，而是**按当前整合包热加载**。

- 启动时只装载底座和当前整合包声明的最小集合。
- 切换整合包时增量装载/卸载（见 [06 §3](06-模式衔接与交接协议.md) 的卸载步骤）。
- 共享插件引用计数归零才真正卸载。

**验证**：切换整合包不需要重启进程。

### 1.3 自举重加载

> 插件加载在依赖上加载，使得插件崩溃不会带崩程序。

三条硬规则（详见 [03 §0](03-装载器与a2a规范.md)）：

1. 依赖序装载，依赖失败则降级不整体失败；
2. 异常由装载器捕获，绝不上抛到主循环；
3. 独立卸载，引用计数管理。

**验证**：任意插件抛异常，进程存活，其他插件正常。

### 1.4 更好的智能体协作

#### 1.4.1 多智能体取一测试

- 1–3~5 智能体**动态决策**（由模型按任务性质定，不是固定数量）。
- 多个智能体**互相争论**后取一。
- 规格见 [09 §4](09-AI能力蓝图.md)。

**智能体 ≠ 会话，两个预算也不是一个。** 智能体是**会话内的执行单元**，用户看不见；会话是**用户可见的对话线程**，有面板、有自己的整合包和工作区。`agentCount` 是**横向**的（一次任务内部起几个），跨会话派活的 `maxDepth` 是**纵向**的（B 还能往下派几层）。实现时别合成一个计数器。

**跨会话派活不是"多智能体"的一种** —— 它派给的是另一个**用户可见的会话**，不是 `agent-pool` 里的一个 `AgentHandle`。区别见 [12 §8.2](12-TypeScript接口契约.md)。

#### 1.4.2 更好的汇报（类公文式汇报）

固定三段式，见 [§2](#2-公文式汇报三段式)。

#### 1.4.3 更好的讨论

- 上下文**记忆链式存储**（有序，非无序集合）。
- 以**编组**形式共享上下文（一次给一组，不各自复制）。
- **动态搜索**智能整合：按需检索，不全量塞进上下文窗口。
- 形成**随心问、随心答**的知识点，不打断，易整合。

规格见 [09 §6](09-AI能力蓝图.md)。

### 1.5 工作台设计（整合包）

三种形态：项目制 / 对话式 / 助手式。详见 [10 §3](10-工作台与项目管理.md)。

- 项目制：平时状态（启动管理）→ 执行过程（讨论/计划/工作/微调修正，管理时间轴）→ 汇报状态（公文式 + CI）。
- 对话式：侧边讨论、截图式同步（全屏信息 + 截图位置）、结束总结式。
- 助手式：只保留基础问答 + 状态汇报。

### 1.6 接口预留

首期就要留出接口，即使不实现完整功能：

| 预留项 | 说明 |
|---|---|
| **语音 TTS 输出** | 语音助手整合包需要。TTS 作为插件预留 |
| **按键信息输入：小键盘** | 高效输入场景预留 |
| **智能语音输入（4B 以下模型）** | 更好的边缘化部署。小模型本地跑，隐私友好，隐私敏感场景必需 |

**为什么首期就留**：语音是入口级能力，接口不定死会导致后续重构。

### 1.7 沙箱运行

插件在沙箱内运行（见 [10 §1](10-工作台与项目管理.md) 的 APP 沙箱）。

- 沙箱是插件的执行环境之一，与核心元件通过映射通信。
- 任务级"新建空间"是沙箱的一种形态（见 [09 §7](09-AI能力蓝图.md)）。
- 沙箱崩溃不影响核心元件。

| 预留项 | 说明 |
|---|---|
| **Windows Office** | Word / Excel / PPT / Outlook。COM 自动化为主，CLI 兜底（见 [03 §2](03-装载器与a2a规范.md) 办公工具） |
| **LSP** | 语言服务协议。支撑 IDE 体验和代码智能 |

### 1.9 模块化设计

功能以**插件/套件为模块独立存在**，跨模块只走接口。

落实到工程结构上，这是**硬性的目录约定**：

| 粒度 | 结构 |
|---|---|
| 核心部分 | **一个文件夹** |
| 每个整合包 | **一个独立文件夹 + 一份开发文档** |
| 每一项功能 | **一个独立插件文件夹** |

整合包**不是内置的**。系统不预置任何整合包 —— 每个整合包都是一个独立开发单元，有自己的文件夹、清单和开发文档，底座只提供装载能力。

详见 [README 目录结构](README.md)。

### 1.10 账号（多模型管理，替代 ccswitch）

**用来替代 ccswitch 这类外部代理，方便一个 Agent 可以使用多种模型。**

- **归属底座**，不是插件、不是套件 —— 模型访问是所有能力的公共依赖。
- 多账号并存，运行时按策略选择，**不依赖外部代理进程，不需重启**。
- 可按任务类别选模型：规划用 A、编码用 B、审查用 C。
- 凭据只存引用，不进上下文、不进日志明文。
- 每次选择写进日志埋点。

与伪装层的两级解耦：**账号决定"调谁"，转化器决定"怎么调"。** 换账号不换转化器，换转化器不换账号。

详见 [10 §2.3](10-工作台与项目管理.md)。

### 1.11 全程日志埋点（模型路径可追踪）

**全程日志埋点，指的是模型路径可追踪。**

- **全系统每一次模型调用都必须留痕**，形成从用户输入到最终产出的**完整可回放调用链**。
- **归属底座**，横跨三层：agent 层记模型/工具/人工编辑，伪装层记转化器/渠道，网络层记出口 IP/缓存/供应商。
- **没有旁路**：底座不提供"跳过记录"的接口。
- **全量无条件**：没有档位，没有"低配模式"。性能与链路追踪的采样是部署配置，不是等级开关。
- 脱敏后再写入；脱敏规则版本化受控，规则版本进链。
- 与交接事件关联，**跨模式追踪不中断**；**跨会话派活不中断** —— 见下。

**跨会话派活产生的是一条 Trace 树，不是几条断链。** A 派活给 B 记一条 `kind: "dispatch"` 的 span，带 `parentTraceId` 指向 B 的 Trace；B 侧也记一条指回 A。B 的每一次模型调用**照样全量无条件记录**，B 的 Trace 一样完整可回放。

**让掉的是"把两个会话的 span 合成一棵树"，不是"记录"。** 合成的话 A 的上下文会被 B 的执行过程污染，A 的 trace 再也读不出「A 这次到底做了什么」。

不要把这条读成"跨会话可以少记"。判据是 [§4](#4-冲突时的优先级) 第 2 条「可追踪 > 便利性」：让掉的是**呈现方式**（A 的 trace 里不展开 B 的细节），不是**记录本身**。契约见 [10 §2.4.4](10-工作台与项目管理.md)。

详见 [10 §2.4](10-工作台与项目管理.md)。

## 2. 公文式汇报三段式

所有汇报**固定**三段，顺序固定：

```text
1. 完成了什么
2. 存在什么问题
3. 需要我做什么决策
```

### 2.1 为什么固定三段

- **第 1 段回答"进度"**——用户最常问的。
- **第 2 段回答"风险"**——主动暴露问题，不让用户自己发现。
- **第 3 段回答"下一步"**——把需要人判断的事挑出来，不让 Agent 替用户拍板。

三段缺一不可，**尤其第 2、3 段**：只报完成不报问题是不诚实的；把需要决策的事自己定了是越权的。

### 2.2 汇报格式可按整合包配置

```ts
interface ReportFormat {
  id: string;
  sections: Array<{
    key: "completed" | "issues" | "decisions" | "nextSteps" | "evidence";
    title: string;              // 源语言字面量，同时是 i18n 的兜底
    /** 固定段用 key 判存在，不拿 title 的字面判 */
    required: boolean;          // completed/issues/decisions 默认 true
  }>;
  /** 证据要求：Agent 自查必须有证据 */
  requireEvidence?: boolean;
  outputFormat: "markdown" | "json" | "html" | "cli" | "voice";
}
```

**`completed` / `issues` / `decisions` 三段恒为必填**，不可被整合包裁掉。可以加段（如 `evidence`），不能减段。

**`title` 允许本地化，接 `i18n` 插件**（见 [12 §8.3](12-TypeScript接口契约.md)）。判定三段在不在**看 `key` 不看 `title`** —— 否则英文会话下「汇报恒为三段：完成了什么 / 存在什么问题 / 需要我做什么决策」这条验收字面失效。

`i18n` 缺失或该 locale 没译文时，`title` 回落源语言字面量，**不空掉**。这条是 `i18n` 插件的降级要求，不是 `ReportFormat` 的新字段。

## 3. 四条功能约束

> 原始素材：`实现功能.md`（2026-07 草稿）

### 3.1 方案通过勾选

不用切换模式、不用勾选，**自动新建子智能体**。

```ts
interface PlanApproval {
  /** 勾选即批准 */
  checks: Array<{ id: string; label: string; checked: boolean }>;
  /** 通过后：自动新建子智能体，而不是等用户切模式 */
  onApproved: "spawn-subagent";
}
```

- 用户在计划态**勾选**通过，不需要切换模式。
- 通过后系统**自动新建子智能体**去执行，不要求用户手动选整合包。
- 勾选项本身进入上下文（作为已确认决策），交接时传递给下游。

### 3.2 断开流式重复（不用补继续）

流式输出断开后**不重放、不追加"继续"**。

```ts
interface StreamRecovery {
  mode: "discard-and-restate";   // 唯一允许的模式
  /** 断开后：丢弃残缺增量，向模型请求"重新完整回答" */
  // 禁止：resend-partial / append-continue
}
```

理由：追加"继续"会导致内容重复、逻辑断裂，且难以判断哪部分是原有、哪部分是新增。**宁可重算一次，也不要拼接出错的答案。**

- 丢弃已接收的残缺增量。
- 用完整上下文重新请求，让模型重新给一个完整答案。
- 已确认的决策和制品引用不受影响（它们在上下文存储里，不在流里）。

### 3.3 对特殊词汇进行清洗

- 特殊词汇、专有名词、术语在**进入上下文前**清洗/规范化。
- 清洗规则由整合包 `promptPolicy` 提供（在输入转化器执行，见 [03 §6](03-装载器与a2a规范.md)）。
- 清洗结果与原词都保留：`raw` 保底，`normalized` 供模型使用。

```ts
interface NormalizationResult {
  raw: string;
  normalized: string;
  appliedRules: string[];
  /** 需要人工确认的歧义项 */
  ambiguous: Array<{ term: string; candidates: string[] }>;
}
```

- **歧义项不静默替换**：置信度不足时保留 `ambiguous`，让用户确认，而不是猜一个。
- 低置信度的语音输入必须触发澄清，不直接执行。

### 3.4 各个工具的使用

工具按类别统一管理，类别包括：**编写 / 计算 / 建模 / 绘画 / 攻击渗透**。

```ts
type ToolCategory = "write" | "compute" | "model" | "draw" | "pentest";

interface ToolManifest {
  // ...
  category: ToolCategory;
  /** 风险等级。pentest 类必须显式授权 */
  riskLevel: "safe" | "elevated" | "privileged";
}
```

| 类别 | 工具举例 | 风险级别 |
|---|---|---|
| **编写** | 文件写入、代码生成、格式化 | safe |
| **计算** | 终端执行、构建、测试 | elevated |
| **建模** | 数据建模、架构设计 | safe |
| **绘画** | 图像生成、SVG 绘制 | safe |
| **攻击渗透** | 渗透测试、漏洞验证 | **privileged**（必须显式授权 + 审计） |

- **风险级别与权限分离**：`riskLevel` 决定默认是否需要确认，`permissions` 决定实际能不能调。两者取交集。
- **攻击渗透类**属于 privileged：需要显式授权，全程审计。**审计无条件，不按等级开关。**
- 工具**按类别注册**，整合包按类别申请，而不是一个个列举。

## 4. 冲突时的优先级

当两条约束冲突时，按此优先级裁决：

1. **安全与审计** > 功能完整
2. **可追踪** > 便利性   ← 全程日志埋点没有旁路，这条不可让
3. **主核心单薄** > 便利性
4. **可替换** > 性能
5. **降级可用** > 一步到位
6. **本地优先** > 云端便利

举例：为了性能想把供应商硬编码进运行时 → 违反第 4 条，改用转化器。
举例：为了少写代码想给模型调用加个"跳过埋点"的开关 → 违反第 2 条，不予采纳。

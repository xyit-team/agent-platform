# 插件 · 中转站

| 项 | 值 |
|---|---|
| `id` | `relay-hub` |
| 所属分类 | 适配 |
| 风险级别 | `elevated`（要探外网、要拿凭据去试） |
| 依赖插件 | 无 |
| 状态 | ⬜ 待开发 |

## 1. 目标

**替代 ccswitch 的"名录"那一半。**

ccswitch 存的是一堆 provider 配置：厂商、baseUrl、可用模型、key。本插件存同样的东西，但多三件事：加站不用手改 json、模型名能对齐、体检能查出哪个模型真的能用。

| | ccswitch（外部） | 本插件 |
|---|---|---|
| 存什么 | 一堆 provider 配置 | 中转站名录：厂商、baseUrl、模型名、凭据引用 |
| 加一个站 | 手改配置文件 | `register()` 一条，带体检 |
| 选哪个 | 点一下 | 选账号时按站筛（账号是核心的，见 [../../../开发文档/10-工作台与项目管理.md](../../../开发文档/10-工作台与项目管理.md) §2.3） |
| 模型名 | 照抄 | **可映射**（站上叫法与官方不同） |
| 可审计 | 无 | 每次物化账号都进埋点 |

## 2. 归属理由

**不进核心。** 核心不该知道市面上有哪些第三方中转站 —— 那是外部世界的信息，会变、会死、会新增。核心只持有 `ModelAccount`，账号长什么样与本插件无关。

**不并进账号管理。** 两者管的不是一件事：

```text
relay-hub  →  外面有哪些站          （会变、会全灭）
账号       →  我现在用哪一个        （必须常驻，所有模式都要用）
```

站可以全灭，账号机制照常。做成插件还有个好处：没装 `relay-hub` 时账号机制照常工作，只是加站要手写 `ModelAccount`。

**不并进 `cli-profile`。** `cli-profile` 管"怎么让 CLI 读到那份配置"，本插件管"那份配置该是什么"。**它不知道 CLI 是什么。**

> **「中转」在库里有两处，别混。**
> ① `SuiteEndpoint.route: "direct" | "relay"` —— **平台自己的转发节点**，见 [../../../开发文档/05-云端套件双体结构.md](../../../开发文档/05-云端套件双体结构.md) §6。
> ② `ModelAccount.kind: "relay"` —— **第三方中转站**，就是本插件管的东西。
> 两者没有继承、没有交叉引用。

## 4. 接口契约

```ts
interface RelayHub {
  list(): RelayStation[];
  register(station: RelayStation): void;
  remove(id: string): void;

  /** 探活 + 逐模型可调用性。**连通不等于能用** */
  probe(id: string): Promise<StationReport>;

  /** 站 + 模型 → 平台账号。账号是核心的，这里只做物化 */
  materialize(stationId: string, alias: string): ModelAccount;
  /** 反查：这个账号是从哪个站来的 */
  originOf(accountId: string): { stationId: string; alias: string } | null;
}

interface RelayStation {
  id: string;
  label: string;
  baseUrl: string;
  /** 站上暴露的模型名 → 平台侧模型名 */
  models: Array<{ alias: string; upstream: string; contextLimit?: number }>;
  credentialRefs: string[];      // 可能有几把 key。只存引用
  health: "unknown" | "healthy" | "degraded" | "dead";
  lastProbedAt?: string;
}

interface StationReport {
  stationId: string;
  reachable: boolean;
  latencyMs?: number;
  models: Array<{ alias: string; ok: boolean; reason?: string }>;
}
```

**契约要求**：
- 输入输出用 `SchemaRef` 声明，运行时校验
- 失败时抛 `PluginError`（带 `code`），由装载器捕获，**不上抛到主循环**
- 凭据只以 `CredentialRef` 出现在这里，**本插件不持有明文**

## 5. 模型名对齐

**站挂一个 `claude-opus-5-5` 的名，背后未必是同名模型。** `models[].alias` / `upstream` 就是干这个的：

```text
站上叫              平台侧叫             对齐
claude-opus-5-5     claude-opus-5-5     alias = upstream
claude-opus-5-5-hd  claude-opus-5-5     alias ≠ upstream —— 站加了自己的后缀
opus-5.5            claude-opus-5-5     站用的是完全不同的叫法
```

**别名对不上就 `accepts()` 拒绝并说明原因，回落 API，不猜。** 猜对了是运气，猜错了是账单。

## 6. 权限

| 权限 | 理由 | 必需 |
|---|---|---|
| `net` | 探活要发请求，试模型要真调一次 | 是 |
| `fs:read` | 读已注册站的缓存报告 | 否 |

**没有 `fs:write`。** 本插件不碰用户家目录、不写配置文件 —— 那是 [../cli-profile](../cli-profile/开发文档.md) 的事。

**实际可用 = 本插件声明 ∩ 整合包授权。** 本插件多声明无效。

## 7. 降级策略

| 情况 | 行为 |
|---|---|
| 站不可达 | 标 `dead`，**明确告知**，不静默换站 |
| 站活着但某模型不可用 | 该模型 `ok: false` + 原因，**其余模型照常可用** |
| 凭据取不到 | 标 `degraded`；账号标 degraded，走已有健康度机制 |
| `materialize()` 传的 alias 站上没有 | **抛错并列出站上实际有的模型名**，不返回空账号 |
| 已物化的账号，站后来被删 | 账号**继续可用**（baseUrl 已在账号上），只是不再可反查 |
| 探活连续失败 | 降为 `degraded` 不立刻 `dead` —— 一次失败可能是网络抖动 |

**通用原则**：降级必须可见。不可用就是不可用，用户要知道原因。

## 8. 验收

- [ ] `register()` 就能加一个站，**不需要手改任何配置文件**
- [ ] `materialize()` 产出的账号 `kind: "relay"` 且带 `relayBaseUrl`
- [ ] `originOf()` 能把物化出来的账号反查回站和别名
- [ ] 别名不存在时**抛错并列出实际有的模型名**，不返回空账号
- [ ] `probe()` 能区分「站不通」和「站通但某模型不可用」
- [ ] **凭据只以 `CredentialRef` 出现**，本插件任何地方不持有明文
- [ ] 探活请求**不带任务内容**，只有最小探测载荷
- [ ] 拿掉本插件后账号机制照常工作，只是加站要手写 `ModelAccount`
- [ ] 每次物化进日志埋点（模型路径的第一段）

- [ ] 全部操作进日志埋点（模型路径可追踪）
- [ ] 单独装载本插件成功，单独禁用后其余正常

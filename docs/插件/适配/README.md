# 适配域

> 19 个插件。解决两件事：**调用各家的模型**，以及**把别人家的 agent CLI 接进来**。
> 一句话：**让不同模型/不同 CLI 在同一套契约下用起来，且不互相污染。**

## 1. 为什么要做

你原本的说法是"提示词和调用要用专武"。这里其实是**两件独立的事**，混在一起做会出问题：

| | 协议适配 | 提示词适配 |
|---|---|---|
| 是什么 | 线格式、工具调用、流式、token 计数、错误码 | 系统提示结构、工具调用约定、缓存与推理块处理 |
| 搞错的后果 | **崩** | **静默降级** —— 还能跑，但质量掉 |
| 会不会漂移 | 会，但慢 | **会，而且快** |
| 插件 | `adapter-*` 六个 | `prompt-*` 五个 |

还有第三件常被塞进上面任何一件：**这个账号怎么到得了**。官方直连 API 就到；中转要**先把配置送到外部 CLI 读得到的地方**。见 [§7.3](#73-中转账号：怎么到得了)。

## 2. 轴不是厂商，是模型家族 + 版本

**厂商是分发商，不是差异来源。** 更要命的是同一厂商不同版本的约定也会变。

所以适配器**必须钉死 `model id + 版本区间`**：

```ts
{
  models: [
    { exact: ["claude-opus-5-5", "claude-sonnet-5-5"] },   // 精确
    { range: { min: "gpt-5.0", max: "gpt-5.9" } },
  ],
  // 超出区间 → 主动拒绝，走 passthrough，不硬用
}
```

不钉版本的后果：你按 v3 的约定写适配器，模型升到 v4，你**不会报错**，只会看到质量慢慢下滑，然后花两天找原因。

## 3. 边界：机制进核心，适配进插件

| | 核心持有 | 插件提供 |
|---|---|---|
| IR 定义 | ✅ | |
| 适配器接口 | ✅ | |
| passthrough 兜底 | ✅ 裸核自带 | |
| 家族适配 | | ✅ |
| CLI 接法 | | ✅ |
| 中转站名录 | | ✅ `relay-hub` |
| CLI 读哪份配置（检测注入 + 注入） | | ✅ `cli-profile` |
| 多语言资源（提示词 / 词条 / 文案） | | ✅ `i18n` |

**为什么机制要进核心**：裸核 + 任何端点都得能跑。大多数端点 OpenAI 兼容，一个 passthrough 默认实现就够了，核心不该为空转。

**为什么适配进插件**：换家族要能独立装、独立关。关掉 Claude 适配不该影响 OpenAI 适配。

## 4. 三个最容易翻车的地方

这才是适配层真正的价值。**这三条搞错了都不报错，只是结果不对。**

### 4.1 工具调用的配对语义

| 家 | 形态 |
|---|---|
| Anthropic | `tool_use` 与 `tool_result` **必须紧邻**，配在同一个 user turn 里 |
| OpenAI 系 | `tool` 是**独立的 message**，`tool_call_id` 关联 |

搞错的症状：**表面上还在跑，工具结果全错位。** 没有异常，没有报错，只是结果不对。

→ [adapter-toolcall](adapter-toolcall/开发文档.md) 专门处理，配对失败**拒绝该轮**，不带着错状态继续。

### 4.2 推理块的回传

Anthropic 的 `thinking` 块**必须原样回传**，不能改写、不能摘要、不能只传摘要。OpenAI 系各家的 reasoning 字段名还都不一样（`reasoning_content`、`reasoning`、厂商私有字段……）。

搞错的症状：**推理静默消失**，回答质量下降但不崩。

→ [prompt-claude](prompt-claude/开发文档.md) / [prompt-openai](prompt-openai/开发文档.md) 的降级规则里写死了：**不认得的推理字段原样透传，绝不丢。**

### 4.3 缓存断点

| 家 | 机制 |
|---|---|
| Anthropic | 要**显式标** `cache_control`，位置标错就完全不命中 |
| OpenAI 系 | 自动缓存，你控制不了 |

搞错的症状：**账单**。多花几倍 token，或者该命中没命中。

→ `cache()` 能力 + 降级规则"放不下就放弃缓存，**明确告知这次没缓存**"。

## 5. 适配器契约

**双向、纯函数、无 IO。**

```ts
interface Adapter {
  // 出：厂商格式 → IR
  toIR(raw: unknown, modelId: string): Canonical;
  // 入：IR → 厂商格式
  fromIR(canonical: Canonical, modelId: string): unknown;

  supports(modelId: string): boolean;
  models: Array<{ exact?: string[]; range?: { min: string; max: string } }>;
  /** 往返转换丢失的字段名。往返后查这个 */
  lossy?: string[];
}
```

| 要求 | 为什么 |
|---|---|
| 纯函数，无 IO | 可单测，适配错误在测试里暴露而不是在生产里 |
| 双向 | 响应也要适配回来，不只出方向 |
| 未知字段**透传不丢** | 适配器吞字段 = 静默丢信息 |
| 有损字段要标出来 | 往返转换后能知道丢了什么 |
| 版本区间超出即拒绝 | 不硬用陈旧约定 |

**N×M 问题的解法**：没有 IR 的话，3 个模型 × 5 个端点 = 15 套对接。有了 IR，是 3 + 5 = 8 个方向。

## 6. 未知模型怎么办

```text
model id → adapter-registry.select()
   命中、版本在区间内 → 用家族适配器
   命中但版本超区间   → 该适配器主动拒绝，走兜底
   没命中             → prompt-passthrough，记入埋点
```

**轴是模型家族 + 版本，不是模型名，更不是账号。**

**为什么适配器不看账号类型**（这条容易在后来被当成漏改）：账号的 `kind: "official" | "relay"` 决定的是**怎么到得了**（[§7.3](#73-中转账号怎么到得了)），不是**按什么格式调**。

曾经设计过"中转账号不许套家族适配器"，理由是中转可能不原样回传推理块、不认 `cache_control`、工具语义有偏差。**这个闸防不住任何东西** —— [§4](#4-三个最容易翻车的地方) 那三条，对第三方中转、对**平台自己的网关**（每个请求都过它）、对任何中间代理**一视同仁**。按账号分流只会给人一个"中转已经被处理过了"的错觉。

真正的防护在两处：**网关透射性契约**（[../../开发文档/02-平台底座-后端底层架构.md](../../开发文档/02-平台底座-后端底层架构.md) §3.2）和有损字段显式标出 + 埋点可审。

**永远不阻断。** 兜底是底线，不是降级。

`prompt-passthrough` 有个反向用途：**兜底占比过高是"该补适配器"的信号**，可以从埋点里直接读出来。

## 7. 外部 CLI 接进来（另一半意思）

`target-resolve` / `cli-bridge` / `cli-sandbox` / `cli-profile` / `relay-hub` / `cli-claude` / `cli-generic` 是另一层：**不自己调模型，而是把别人已经调好的 agent CLI 当子进程跑。**

**为什么值得**：Claude Code、Codex、Gemini CLI **自带 agent 循环、文件访问、工具链、上下文管理**。调它们等于白拿一整套成熟 harness。

| 适合 | 不适合 |
|---|---|
| 复杂长任务、它那套 harness 已经调好了 | 需要精细控制每一步的时候 |
| 一次性委派，只要结果 | 要全程埋点、每步可追溯 |
| 跑在隔离工作区里的脏活 | 接触用户标注为敏感的数据目录 |

**代价说清楚**：

| 代价 | 处理 |
|---|---|
| 黑盒 —— 里面发生什么看不见 | 接受，或者不用 |
| 难埋点 —— 它自己的调用链不归你管 | 至少记「调了它、参数、返回」这一层 |
| 结果回流要解析 | `parse()` 失败保留**全量原文** |
| 它也在模型路径上 | **必须记入埋点**，否则「模型路径可追踪」就漏了一块 |

**隔离不是可选项** —— 它是外部程序。`cli-sandbox` 隔离不可用时**直接拒绝启动**，不降级裸跑。

### 7.1 走 API 还是走 CLI —— 解析链

**模型名可以自动匹配到 CLI，也可以由人选定。** 但匹配是**便利**，不是**同一性**：

- 键名带 `claude-` 前缀，但那是第三方中转站的 key，认证对不上
- 任务只是"翻译一段话"，匹配到 CLI 是杀鸡用牛刀，还要开进程开工作区
- 外部 CLI 不得接触用户标注为敏感的数据目录，但模型名照样匹配得出来

所以解析链有固定优先级：

```text
① 显式指定（人指定的，永不被覆盖）
② 整合包 profile 声明
③ 粘性（人上次选过，理由是「上次你选的」不是「自动匹配」）
④ 自动匹配模型名（每次都要告知，不默默跑外部程序）
⑤ API 兜底
```

| 规则 | 为什么 |
|---|---|
| 显式永不被覆盖 | 人说过的话不能被启发式推翻 |
| 自动匹配到 CLI **每次告知** | 外部程序在跑，你有权知道 |
| 粘性要能查能清 | 人可能忘了自己选过 |
| CLI 起不来 → **回落 API** | 否则自动匹配会让系统变脆弱 |
| 匹配上但 `accepts(account)` 为 false → 回落 API | 键名对得上不代表认证兼容 |
| 并行可表达 | API 探索 + CLI 收敛是常见组合，不是二选一 |
| **自动匹配被整体关闭**（账号或整合包层面） | 只允许人工选，默认走 API |

每一步都能用 `explain()` 说出为什么，以及上游各级为什么没选中。

### 7.2 与核心的分工

```ts
ModelSelectionPolicy（核心）→  哪个账号、哪个模型
relay-hub（插件）            →  外面有哪些第三方中转站
target-resolve（插件）       →  走 API 还是走 CLI
cli-profile（插件）          →  让 CLI 读到该读的那份配置
```

核心的 `ModelSelectionPolicy` **只决定模型，不因本插件增减而变**。「走 API 还是 CLI」是可插拔增强 —— 大多数情况走 API，CLI 插件没装就没有 CLI 通道。

关掉 `target-resolve`，全部回落 API，模型调用不受影响。关掉 `relay-hub`，账号机制照常，只是加站要手写 `ModelAccount`。

### 7.3 中转账号：怎么到得了

> **「中转」在库里有两处，含义不同。**
> ① `SuiteEndpoint.route: "direct" | "relay"` —— **平台自己的转发节点**，见 [../../开发文档/05-云端套件双体结构.md](../../开发文档/05-云端套件双体结构.md) §6。
> ② `ModelAccount.kind: "relay"` —— **第三方中转站**，就是这一节讲的。
> 两者没有继承、没有交叉引用。

**ccswitch 由三样东西替代，各管一段，不重叠**：

| | 是什么 | 谁 |
|---|---|---|
| **中转站名录** | 外面有哪些站、各自哪些模型、怎么体检 | `relay-hub`（插件） |
| **账号** | 我现在用哪个模型、哪把 key | 底座核心 |
| **注入** | 怎么让外部 CLI 读到那份配置 | `cli-profile`（插件） |

**不导入 ccswitch 的配置文件** —— 那是让平台依赖一个要被替代的东西。

#### 到 CLI：先检测，没用才注入

CLI 有自己的认证模型，它不认"平台传给我的 baseUrl + key"。要走中转站，就得**让 CLI 自己读到那份配置**：

```text
detect(cli, account) → absent | matching | mismatched | partial
     ↓
ensure()  ── matching ──→ 一个字节都不写，直接开跑
         └─ 其余 ──────→ 注入，走 A 或 B
```

**`matching` 是检测的全部价值。** CLI 会话反复用同一份配置，每次重写既慢，又把配置暴露在"被外部改动"的窗口里。

**判据只取三项**（`baseUrl` / `keyHash` / `model`）—— 配置格式会变，窄抽取能扛漂移。`keyHash` 存 sha256 不存明文，所以指纹能整个进埋点、能事后审"这次用的哪把 key"。

| | A 环境变量隔离 | B 备份改写恢复 |
|---|---|---|
| 做法 | 起进程时把配置目录指到我们造的那份 | 改用户真配置，跑完改回来 |
| 动用户的东西 | **一点不动** | 动了 |
| 崩了的后果 | 临时目录留下，**无影响** | **配置卡在中转态** |
| 并发 | 能 | **不能**，要抢锁 |
| ccswitch 用哪种 | — | B |

**默认 A，B 是降级。** B 的四个坑（先写后 spawn、备份落固定路径 + 下次启动查残留、拿不到锁就回落 A 不排队、恢复后比哈希）见 [cli-profile §7](cli-profile/开发文档.md)。

**CLI 会话直接排除 B** —— 用户真配置会在整个 CLI 会话期间停在别的站上，暴露窗口从一个任务拉长到一个 CLI 会话。

**CLI 会话禁止 B。**

### 7.4 CLI 会话与结果

外部 CLI 的启动成本（拉进程、建 agent 循环、灌上下文）在多次询问里摊薄得很快，所以会话是常驻的。

| | 行为 |
|---|---|
| **空闲自退** | 默认 5 分钟无询问就优雅退出，`exitReason: "idle-timeout"`。**不是可选项** —— 没有自退的 CLI 会话等于常驻泄漏 |
| **重建** | 带 `resumeToken` 重新打开，接上同一份 CLI 上下文 |
| **切绑定** | 老会话**跑完为止**，等它退完新会话才带 `resumeToken` 接管。**不打断正在跑的那一问** |
| **方式 B** | **CLI 会话禁用** |
| **收尾** | 会话退出或超时自退时 `CliSandbox.revoke()` 回收授权 |

**结果不截断。** `CliResult.raw` 是全量原文。

**格式要求前置传进 CLI**，不是拿到再裁：让 CLI 第一次就生成对的，比裁更省也更准 —— **裁剪只能删，生成能重排**。格式来自整合包的 `profile.reportFormat`。

**超长不自动裁。** `cli-bridge` 只报 `digest: { reason, bytes }`，**不起子智能体** —— 那是 A2A 的事。整合包在 workflow 层接，必要时调子智能体做压缩总结。`raw` 永远完整进埋点，哪怕被总结了：外部 CLI 的输出是模型路径的一环，裁掉就断链。

## 8. 与账号的关系

```
账号（核心）      →  调谁   —— 决定用哪个模型、哪把 key、怎么到得了
适配域（插件）    →  怎么调 —— 决定用什么格式、什么提示词约定
```

这个分工和 [../../开发文档/02-平台底座-后端底层架构.md](../../开发文档/02-平台底座-后端底层架构.md) §5.2 一致：**账号是底座能力，适配是可插拔的优化。**

账号归核心，因为每个模式都要用；适配归插件，因为**大多数模式用 passthrough 就够了**。

# 整合包 · 设计转代码

> 示例整合包。格式见 [../../开发文档.md](../../开发文档.md)。
> **本文只写：由哪些插件完成。**

## 1. 目标

把设计稿（截图、Figma 链接、现有页面），变成**能跑起来、样式对得上的页面**。

**实现型整合包** —— 产出界面。与代码开发共享大部分插件，差别在**输入是图不是需求**。

### 1.1 模型策略

```ts
modelPolicy: {
  transport: "auto",
  byTaskKind: {
    read:     ["claude-opus-5-5"],   // 看图要求强推理：布局、间距、层级都要读对
    spec:     ["claude-sonnet-5-5"],
    implement:["claude-sonnet-5-5"],
    verify:   ["claude-opus-5-5"],   // 对比设计稿和实现差在哪
  },
}
```

**`read` 和 `verify` 都不能降级到便宜模型。** 这两步是"看起来对不对"的判断，而**判断错了不报错** —— 一个间距差 8px 的页面能跑、能测试通过，只是跟设计稿不一样。人要靠肉眼发现，正是这里没做对。

跟代码开发包一样，`implement` 走外部 CLI 白拿 harness；`transport: "auto"` 让 `target-resolve` 决定具体走哪条。

## 3. 状态

```text
讨论 → 计划 → 工作 → 微调修正 → 汇报
```

| 状态 | 在做什么 | 验证 hook |
|---|---|---|
| **讨论** | 对齐设计稿：哪个是主稿、多端怎么排、交互态有几个 | 关键页面已框选确认 |
| **计划** | 拆组件树、定实现顺序、建工作区 | 组件树可执行 |
| **工作** | 写组件 → 跑 dev server → 截图对照 | `verify.typecheck`、`verify.build` |
| **微调修正** | 视觉对不上时修 | 重新截图对照 |
| **汇报** | 页面交付汇报 | 三段齐全 |

**关键规则**：

| 规则 | 说明 |
|---|---|
| 截屏**全屏尺寸和区域都留** | 区域框选会丢上下文，全屏图必须有 |
| 视觉对照用截图，不用"我觉得像" | 改完截一张，和设计稿并排比 |
| 设计稿没说清的交互态**主动问** | hover / 加载 / 空 / 错误 四态默认要问 |
| 改配色、间距走 token 不写死值 | 便于后续统一调整 |
| 已有项目里**先看现有组件** | 不重复造 |

## 4. 交接

### ← 语音助手 / 代码开发（入）

需求已明确、含界面部分时进来。

### → 代码开发（出）

页面骨架通过后，交互逻辑、数据层、接口对接交给代码开发。

```ts
{
  targetPackageId: "code-development",
  trigger: "完成条件",
  requiredFacts: ["projectId", "componentTree", "designRefs", "commitRef"],
  handoffMapping: {
    "design.componentTree": "task.constraints",
    "design.refs":          "history.artifactRefs",   // 设计稿截图引用
    "project.id":            "task.projectId",
    "project.commitRef":     "project.baselineCommit",
  },
  prepare: [
    { kind: "language",     value: "typescript" },
    { kind: "framework",    value: "react" },
    { kind: "reportFormat", value: "code-development/change-report" },
  ],
}
```

**设计稿截图引用一并传过去** —— 后续调样式时还要对得上。

### → 项目监测（出）

页面可交付且有可观测检查点后。

## 5. 汇报格式

```ts
{
  id: "design-to-code/ui-report",
  sections: [
    { key: "completed", title: "完成了什么",     required: true },   // 做了哪些页面/组件
    { key: "issues",    title: "存在什么问题",   required: true },   // 对不上的地方、缺的交互态
    { key: "decisions", title: "需要我做什么决策", required: true },  // 设计稿没定的怎么定
    { key: "contrast",  title: "设计稿对照",     required: true },   // 实现截图 vs 设计稿
  ],
  requireEvidence: true,
  outputFormat: "markdown",
}
```

**对照段是本整合包特有的** —— 前后各一张图，标出差异。

## 6. 权限

| 权限 | 理由 | 必需 |
|---|---|---|
| `fs:read` `fs:write` | 读写组件与样式 | 是 |
| `device` | 截屏、截图对照 | 是 |
| `process` | dev server、构建 | 是 |
| `net` | 模型调用、设计稿 API | 否（`design-suite` 离线时不需要） |

## 7. 降级

| 缺失 | 行为 |
|---|---|
| `design-suite` 离线 | 只能用截图做，**明确告知精度受限** |
| `screen-capture` 不可用 | 无法做视觉对照，**不允许进汇报态** |
| `dev server` 起不来 | 降级为静态渲染预览，**明确告知** |
| `model-suite` 离线 | `local-model`，**明确告知** |
| 浏览器不可用 | 用 `visual-render` 的组件树代替实际渲染，**明确告知** |

## 8. 验收

- [ ] 截屏同时保留**全屏图和区域图**
- [ ] 每个页面有实现截图可与设计稿并排比
- [ ] hover/加载/空/错误四态**主动问过**设计稿没说的
- [ ] 优先复用现有组件，不重复造
- [ ] 交接出去时设计稿引用一并带过去
- [ ] 视觉改动有检查点，能开分支回退
- [ ] 汇报恒为三段 + 对照
